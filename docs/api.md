# API Design

## Status

M0 exposes only an operational health endpoint. Product contracts below are conventions for future endpoints and may evolve through reviewed changes.

## Current endpoint

### `GET /health`

Returns process health without touching external dependencies.

```json
{
  "status": "ok",
  "service": "api",
  "environment": "local"
}
```

- `200 OK`: the API process is running and can serve requests.
- No authentication is required.
- The response must not include secrets, host details, or dependency credentials.

A separate readiness check should be introduced when the API has required dependencies and the deployment platform can use distinct liveness/readiness semantics.

## Contract conventions (planned)

- Product endpoints live under `/api/v1`.
- JSON is the default representation and uses `snake_case` fields.
- Timestamps are RFC 3339 UTC values.
- Public identifiers are opaque UUID strings.
- OpenAPI generated by FastAPI is the source contract, supplemented by examples and workflow documentation here.
- Breaking changes require a new API version or an explicit, coordinated migration.

## Authentication and tenant context (planned)

Authenticated requests use a bearer token from the selected identity provider. Public chat and webhook endpoints will use purpose-specific credentials or signed session/webhook mechanisms.

The API resolves tenant context from verified authorization state. A path, header, query, or body tenant ID can select among authorized tenants but never grants access by itself. Tenant mismatch must fail without revealing whether another tenant's resource exists.

## Error model (planned)

Expected failures should use a stable envelope:

```json
{
  "error": {
    "code": "resource_not_found",
    "message": "The requested resource was not found.",
    "details": {},
    "request_id": "0194f2c8-..."
  }
}
```

- `code` is stable and machine-readable.
- `message` is safe for the caller and must not leak internals.
- `details` contains validated field-level or recovery information where useful.
- `request_id` connects the response to structured logs.

Validation failures should preserve FastAPI/Pydantic detail only after the public format is deliberately selected. Provider payloads, SQL, stack traces, secrets, and cross-tenant hints never belong in responses.

## Pagination, filtering, and idempotency (planned)

- Prefer cursor pagination for mutable, potentially large collections.
- Use deterministic ordering with a unique tie-breaker.
- Bound page sizes and validate filter combinations.
- Use idempotency keys for externally retried creates, webhook deliveries, and job submissions.
- Document retryable status codes and side effects per endpoint.

## Streaming (planned)

The web answer experience is expected to stream status and content. Server-Sent Events are the initial candidate because the primary flow is server-to-client, but the choice should be confirmed in M3/M4. A stream must define event types, terminal/error events, reconnection behavior, cancellation, persistence timing, and citation finalization.

## Documentation and compatibility

- Keep request/response models typed and colocated with the owning capability.
- Add contract tests for critical endpoints and tenant failure cases.
- Include representative examples without real customer data.
- Update this document in the same change as new public conventions.
- Generated clients, if introduced, must be reproducible from a committed contract and must not replace contract review.
