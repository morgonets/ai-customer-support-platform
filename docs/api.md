# API Design

## Status

M1 exposes operational health/readiness checks and an authenticated current-user endpoint. The
organization and membership contracts described later in this document are added with their owning
implementation changes.

## Operational endpoints

### `GET /health`

Returns process health without touching external dependencies.

```json
{
  "status": "ok",
  "service": "api",
  "environment": "local"
}
```

- `200 OK`: the API process is running and can serve requests.
- No authentication is required.
- The response must not include secrets, host details, or dependency credentials.

### `GET /ready`

Checks that the API can connect to its required PostgreSQL dependency. It returns the same success
body as `/health`, or the standard `503 dependency_unavailable` error without connection details.
No authentication is required. Deployment health checks should use `/health` for liveness and
`/ready` for traffic readiness.

## User endpoint

### `GET /api/v1/users/me`

Requires `Authorization: Bearer <access-token>`. The token must have a valid ES256 signature from
the configured Supabase JWKS, issuer, `authenticated` audience and role, timestamps, and UUID
subject.

```json
{
  "id": "0194f2c8-1cf0-7d6b-972c-a71fc21dbbf2",
  "email": "person@example.com"
}
```

The email may be `null` when the provider session has no email claim. Credentials and session
refresh remain Supabase Auth concerns; FastAPI consumes access tokens and never accepts refresh
tokens.

## Contract conventions

- Product endpoints live under `/api/v1`.
- JSON is the default representation and uses `snake_case` fields.
- Timestamps are RFC 3339 UTC values.
- Public identifiers are opaque UUID strings.
- OpenAPI generated by FastAPI is the source contract, supplemented by examples and workflow documentation here.
- Breaking changes require a new API version or an explicit, coordinated migration.

## Authentication and tenant context

Authenticated requests use a Supabase Auth bearer token. FastAPI independently verifies the token
against the configured JWKS and constructs the authenticated actor. It does not trust identity
headers from the web application and it does not read organization roles from JWT claims.

For every product-data transaction, the database dependency installs only the verified subject,
`authenticated` audience, and `authenticated` provider role into transaction-local claims, then
assumes the restricted `app_api` database role. Organization endpoints additionally resolve current
membership and role from PostgreSQL. A path, header, query, or body organization ID can select among
authorized organizations but never grants access by itself. Tenant mismatch must fail without
revealing whether another tenant's resource exists.

## Error model

Expected failures should use a stable envelope:

```json
{
  "error": {
    "code": "resource_not_found",
    "message": "The requested resource was not found.",
    "details": {},
    "request_id": "0194f2c8-..."
  }
}
```

- `code` is stable and machine-readable.
- `message` is safe for the caller and must not leak internals.
- `details` contains validated field-level or recovery information where useful.
- `request_id` connects the response to structured logs.

Validation failures use `validation_error` with sanitized `location`, `message`, and `type` details;
request inputs are excluded. Authentication failures use `401 authentication_required` or
`401 invalid_token` and include `WWW-Authenticate: Bearer`. Provider payloads, SQL, stack traces,
secrets, and cross-tenant hints never belong in responses.

## Pagination, filtering, and idempotency (planned)

- Prefer cursor pagination for mutable, potentially large collections.
- Use deterministic ordering with a unique tie-breaker.
- Bound page sizes and validate filter combinations.
- Use idempotency keys for externally retried creates, webhook deliveries, and job submissions.
- Document retryable status codes and side effects per endpoint.

## Streaming (planned)

The web answer experience is expected to stream status and content. Server-Sent Events are the initial candidate because the primary flow is server-to-client, but the choice should be confirmed in M3/M4. A stream must define event types, terminal/error events, reconnection behavior, cancellation, persistence timing, and citation finalization.

## Documentation and compatibility

- Keep request/response models typed and colocated with the owning capability.
- Add contract tests for critical endpoints and tenant failure cases.
- Include representative examples without real customer data.
- Update this document in the same change as new public conventions.
- Generated clients, if introduced, must be reproducible from a committed contract and must not replace contract review.
