# Database Design

## Status

M1 uses Supabase PostgreSQL as the transactional system of record and Supabase Auth as the
identity store. The committed Supabase SQL migrations create the application schemas, identity
projection, organizations, memberships, roles, grants, and row-level security policies described
below. Knowledge, conversation, vector, billing, and analytics tables remain planned.

## Database role

PostgreSQL owns application state and current authorization state. Supabase Auth owns credentials,
sessions, and records under `auth`; the application references only the stable `auth.users.id`
primary key.

Application code uses SQLAlchemy through a direct PostgreSQL connection. It does not query
application tables through Supabase Data APIs, and browser code has no product-data database
access.

## Schemas and exposure

- `auth`: Supabase-owned identities and sessions. Application migrations do not modify its managed
  tables.
- `app`: application tables. This schema is not in the Supabase Data API exposed-schema list.
- `app_private`: trigger and RLS helper functions. It is also not exposed.
- `public` and `graphql_public`: remain available to Supabase platform components but contain no M1
  product tables.

`anon`, `authenticated`, and `service_role` receive no privileges on `app` or `app_private`.
FastAPI is the exclusive product-data API.

## Conventions

- UUID primary keys for externally visible entities
- `organization_id` as the tenant key on every tenant-owned table
- `created_at` and `updated_at` as timezone-aware UTC timestamps
- Lowercase `snake_case` names
- Explicit foreign keys and deletion behavior
- Tenant-aware unique constraints and indexes
- Database checks for bounded names and the `owner`, `admin`, and `member` role values
- No passwords, tokens, provider credentials, or duplicated Auth email addresses in application
  tables

## M1 schema

### `app.user_profiles`

| Column         | Type          | Rules                                                        |
| -------------- | ------------- | ------------------------------------------------------------ |
| `user_id`      | `uuid`        | Primary key; references `auth.users(id)` with cascade delete |
| `display_name` | `text`        | Optional, trimmed, 1–100 characters when present             |
| `created_at`   | `timestamptz` | Required, database UTC time                                  |
| `updated_at`   | `timestamptz` | Required, maintained by trigger                              |

An `auth.users` insert trigger creates the profile. It copies only a valid bounded display name;
invalid or oversized untrusted metadata becomes `NULL` rather than blocking registration. Existing
Auth users are backfilled when the migration is applied.

### `app.organizations`

| Column               | Type          | Rules                                                                   |
| -------------------- | ------------- | ----------------------------------------------------------------------- |
| `id`                 | `uuid`        | Primary key, generated by PostgreSQL unless supplied by the application |
| `name`               | `text`        | Required, trimmed, 1–100 characters                                     |
| `created_by_user_id` | `uuid`        | Nullable Auth user reference; set null if the creator is deleted        |
| `created_at`         | `timestamptz` | Required, database UTC time                                             |
| `updated_at`         | `timestamptz` | Required, maintained by trigger                                         |

Names are not globally unique. M1 routes use opaque organization UUIDs and do not reserve a slug
contract prematurely. Organization deletion is not exposed in M1.

### `app.organization_memberships`

| Column            | Type          | Rules                                               |
| ----------------- | ------------- | --------------------------------------------------- |
| `id`              | `uuid`        | Primary key                                         |
| `organization_id` | `uuid`        | Required organization reference with cascade delete |
| `user_id`         | `uuid`        | Required Auth user reference with cascade delete    |
| `role`            | `text`        | Required: `owner`, `admin`, or `member`             |
| `created_at`      | `timestamptz` | Required, database UTC time                         |
| `updated_at`      | `timestamptz` | Required, maintained by trigger                     |

`(organization_id, user_id)` is unique. Separate indexes support organization listing by user and
role checks by organization. A serialized trigger rejects deletion or demotion of the last owner,
including an Auth user cascade.

## Runtime roles and transaction identity

- `api_login` is the password-bearing FastAPI login. It has no table privileges and does not
  inherit other roles automatically.
- `app_api` cannot log in, own tables, create objects, or bypass RLS. It receives only the documented
  schema and table privileges.
- `api_login` may assume only `app_api` for product queries.
- The local/production password is provisioned outside migrations. Migration and runtime
  credentials are separate.

For every authenticated request, FastAPI begins a transaction, installs the already verified JWT
claims with transaction-local `request.jwt.claims`, and uses `SET LOCAL ROLE app_api` before the
first product query. Transaction-local state prevents identity leaking when a pooled connection is
reused. Missing setup fails closed because `api_login` cannot read application tables.

## RLS and tenant isolation

All M1 application tables enable and force RLS. Policies are operation-specific and apply only to
`app_api`.

- Profiles: a user may select their own profile and profiles of users who share an organization;
  only the user may update their display name.
- Organizations: members may select their organizations; authenticated users may insert an
  organization only with themselves as creator; owners and admins may update the name.
- Memberships: members may list memberships in their organizations. Owners may add any role;
  admins may add members only. Only owners may change roles. Owners and admins may remove roles
  within the documented hierarchy, and a user may leave, but the last-owner trigger remains final
  enforcement.
- Creation bootstrap: an authenticated creator may add exactly the first owner membership for a
  newly created organization. Organization and membership insertion occur in one API transaction.

Membership helper functions are `SECURITY DEFINER`, use an empty `search_path`, reference only
schema-qualified objects, and are executable only by `app_api`. They avoid recursive membership
policies while retaining the verified `auth.uid()` identity.

RLS supplements, rather than replaces, FastAPI authorization. Application services resolve an
organization membership and role before repository operations, and repositories still include
explicit organization filters. A foreign organization identifier never grants access.

## Future tenant-owned tables

Every future tenant-owned table must add, in the same migration:

- a non-null `organization_id` foreign key
- tenant-aware indexes and unique constraints
- explicit least-privilege grants
- enabled and forced RLS with tests for every granted operation
- tenant-required repository interfaces and FastAPI authorization tests
- documented deletion and retention behavior

## Migration policy

Supabase CLI SQL migrations under `supabase/migrations` are the only schema history. Alembic is not
used. SQLAlchemy mappings are reviewed against migrations but do not generate a second history.

- Applied migrations are immutable.
- `pnpm db:reset` must rebuild an empty local database from all migrations and synthetic seeds.
- `pnpm db:lint` checks database functions and schema objects.
- `pnpm db:test` runs pgTAP schema, grant, role, invariant, and RLS isolation tests.
- CI runs all three commands against the local Supabase stack, then runs the FastAPI repository and
  tenant service against the same PostgreSQL policies inside a rolled-back integration transaction.
- Remote application requires an explicit reviewed `supabase db push --dry-run` followed by a
  controlled push. M1 does not link or modify a remote project.
- Migrations document recovery notes. Once data exists, prefer roll-forward recovery over dropping
  application schemas.
- Seed data is synthetic, deterministic, and credential-free.

## Backup, retention, and deletion

Production project, region, plan, backup/PITR, retention, recovery objectives, and offboarding
policy remain configurable decisions. Before launch, document and test backups, restores, tenant
export/deletion, Auth user deletion, and measured RPO/RTO. M1 does not invent those production
values or expose organization deletion.
